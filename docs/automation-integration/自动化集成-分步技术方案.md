```typescript
  const pendingQueues = await storage.entity('AutomationWebhookQueue')

      status: 'pending',
      retryCount: { $lt: 3 }
```

### T4.1 - T4.9: 详细实现（已完成）

#### 核心决策流程 - 文件变更场景判断逻辑


**完善版闭环决策流程图**:

```
开始处理Commit中的所有文件
    ↓
预处理：过滤和分类所有变更文件
    - 测试文件列表 (filteredTestFiles)
    - 配置文件变更 (configFile)
    - 其他文件 (ignored)
    ↓
判断是否包含配置文件变更 (automation-test-map.json)
    ↓
是 → 进入协调处理模式
      ↓
    1. 验证配置文件完整性
       - 格式错误 → 记录错误，忽略本次配置相关处理，仅处理纯代码变更
       - 解析成功 → 获取新旧配置差异
      ↓
    2. 分析配置变更影响范围
       - 新增映射文件列表 (newMappedFiles)
       - 删除映射文件列表 (removedMappedFiles)  
       - 修改映射文件列表 (changedMappedFiles)
      ↓
    3. 协调处理策略（按优先级执行）：
       A. 先处理删除映射的文件 → 执行操作C1 (删除相关用例)
       B. 再处理修改映射的文件 → 执行操作C2 (模块迁移)
       C. 后处理新增映射的文件 → 执行操作C3 (扫描创建)
      ↓
    4. 处理同时有配置+代码变更的文件
       - 使用最新配置规则
       - 按合并处理逻辑执行 → 操作A (配置+代码变更)
      ↓
    5. 处理其他未受配置影响的测试文件 → 操作B (正常更新)
    ↓
否 → 进入单文件处理模式
      ↓
    对每个测试文件执行闭环决策：
    
    1. 判断是否为新增文件 (diff.new_file === true)
        ↓
      是 → 当前配置中是否有map映射?
            是 → 直接组织新增数据 → CREATE操作
            否 → 忽略该文件，记录日志
        ↓
      否 → 继续下一步判断
    
    2. 判断是否为删除文件 (diff.deleted_file === true)
        ↓
      是 → 删除该文件的所有相关用例 → DELETE操作
        ↓
      否 → 继续下一步判断
    
    3. 判断是否为重命名/移动文件 (old_path !== new_path && !new_file && !deleted_file)
        ↓
      是 → 处理路径变更场景：
            - 检查old_path在配置中的映射状态
            - 检查new_path在配置中的映射状态
            
            情况1：old有映射，new有映射 → 判断模块是否变更
                  模块变更 → 执行操作A (涉及模块变更)
                  模块不变 → 执行操作B (正常更新)
                  
            情况2：old有映射，new无映射 → DELETE操作 + 警告日志
            情况3：old无映射，new有映射 → CREATE操作 (当作新文件)
            情况4：old无映射，new无映射 → 忽略，记录日志
        ↓
      否 → 执行操作B (正常内容更新)

异常处理和边界场景：

错误处理策略：
  - 配置文件解析失败 → 忽略配置变更，仅处理纯代码变更 + 发送告警
  - 单个文件处理失败 → 记录错误日志，继续处理其他文件
  - 批量处理部分失败 → 记录成功/失败统计，不回滚已成功的操作
  - API调用超时/失败 → 重试机制 (最多3次)

事务性考虑：
  - 每个操作独立执行，失败不影响其他文件
  - 记录详细的操作日志，支持手动补偿
  - 提供批量重试接口，处理失败的文件

```

**操作定义**:

```
操作A (配置+代码同时变更):
  处理顺序：先应用配置变更，再处理代码变更
  1. 新增用例 → CREATE + 使用新模块映射
  2. 修改用例 → UPDATE + 同时更新模块
  3. 删除用例 → DELETE
  4. 未变化用例 → MIGRATE (仅修改模块)
  5. 记录复合变更日志

操作B (正常用例更新):
  1. 新增用例 → CREATE
  2. 修改用例 → UPDATE  
  3. 删除用例 → DELETE

操作C1 (删除映射处理):
  1. 查询该映射下的所有相关用例
  2. 批量DELETE相关用例
  3. 记录删除统计

操作C2 (修改映射处理):
  1. 查询该映射下的所有相关用例
  2. 批量MIGRATE到新模块
  3. 记录迁移统计

操作C3 (新增映射处理):
  1. 扫描该文件路径下的所有测试用例
  2. 批量CREATE用例到指定模块
  3. 记录创建统计

降级策略：
  - 配置文件不可用/格式错误 → 忽略配置相关处理，只处理纯代码变更，记录告警
  - 部分API不可用 → 降级为只读模式，记录待处理队列
  - 模块不存在 → 自动创建或分配到默认模块
```

```typescript
function parseDiffLines(diffContent: string) {
  const changes = [];
  const lines = diffContent.split('\n');
  
  for (let line of lines) {
    if (line.startsWith('@@')) {
      // 解析行号范围: @@ -28,7 +30,8 @@
      const match = line.match(/@@ -(\d+),(\d+) \+(\d+),(\d+) @@/);
      if (match) {
        changes.push({
          oldStart: parseInt(match[1]),
          oldLines: parseInt(match[2]),
          newStart: parseInt(match[3]), 
          newLines: parseInt(match[4])
        });
      }
    }
  }
  return changes;
}
```

```typescript
function findAffectedTestMethods(fileContent: string, diffChanges: any[]) {
  const lines = fileContent.split('\n');
  const methods = [];
  
  // 1. 先找到所有测试方法的位置
  for (let i = 0; i < lines.length; i++) {
    if (lines[i].includes('@Test') || lines[i].includes('public void')) {
      // 向上查找@TestId注解
      let testId = null;
      for (let j = i - 5; j <= i; j++) {
        if (j >= 0 && lines[j].includes('@TestId')) {
          testId = extractTestId(lines[j]);
          break;
        }
      }
      
      // 向下查找方法名
      let methodName = null;
      for (let k = i; k < i + 3; k++) {
        if (k < lines.length && lines[k].includes('public void')) {
          methodName = extractMethodName(lines[k]);
          break;
        }
      }
      
      if (testId && methodName) {
        methods.push({
          testId: testId,
          methodName: methodName,
          lineStart: i,
          lineEnd: findMethodEnd(lines, i)
        });
      }
    }
  }
  
  // 2. 判断哪些方法受到diff影响
  const affectedMethods = [];
  for (let method of methods) {
    for (let change of diffChanges) {
      if (isLineRangeOverlap(method.lineStart, method.lineEnd, change.newStart, change.newStart + change.newLines)) {
        affectedMethods.push({
          ...method,
          operation: determineOperation(change, method)
        });
      }
    }
  }
  
  return affectedMethods;
}
```

#### 1. API策略调整 - 从批量API改为单个API并发调用

**问题发现**:

```typescript
// ❌ 原计划：批量API
await bulkCreateItems({ items: [...] });

// ✅ 实际采用：单个API并发调用
const BATCH_SIZE = 5;
for (let i = 0; i < items.length; i += BATCH_SIZE) {
  const batch = items.slice(i, i + BATCH_SIZE);
  const promises = batch.map(item => forgeCreateItem(item));
  await Promise.all(promises);
  
  // 批次间延迟，避免请求过于频繁
  if (i + BATCH_SIZE < items.length) {
    await new Promise(resolve => setTimeout(resolve, 100));
  }
}
```

**最终API列表**:
- **创建**: `POST /parse/api/v2/items` （单个，并发5个/批）
- **更新**: `PUT /parse/api/v2/items/{itemId}?detail=true` （单个，并发5个/批）
- **查询**: `POST /parse/api/search` （IQL批量查询，保持不变）
- **删除**: `DELETE /parse/api/items/bulk` （保持批量）

- 需要维护模块的父子层级关系

**实现方案**:
```typescript
async function resolveRepositoryId(modulePath: string, workspaceKey: string): Promise<string> {
  // 1. 处理根目录标识
  if (pathParts[0] === '全部用例库') {
    pathParts.shift(); // 移除根目录，"全部用例库"不需要创建
  }
  
  // 2. 逐层创建模块
  for (const pathPart of pathParts) {
    // 查询现有模块（注意使用正确的表名）
    const repositoryQuery = getParseQuery(false, RepositoryClassName);
    // RepositoryClassName = 'test_manager_Repository'
    
    const existingRepo = await repositoryQuery
      .equalTo('workspaceKey', workspaceKey)
      .equalTo('name', pathPart)
      .equalTo('parent', parentId ? ... : null)
      .first();
    
    if (!existingRepo) {
      // 创建新模块
      const RepositoryModel = getParseModel(false, RepositoryClassName);
      const repository = new RepositoryModel();
      repository.set('name', pathPart);
      repository.set('workspaceKey', workspaceKey);
      repository.set('parent', parentId ? ... : null);
      
      const [savedRepo] = await saveAllObject([repository]);
      repositoryId = savedRepo.id;
    }
  }
  
  return repositoryId;
}
```

**注意事项**:
- Repository表名：使用`test_manager_Repository`（不是`Repository`）
- 查询时使用：`getParseQuery(false, RepositoryClassName)`
- 创建时使用：`getParseModel(false, RepositoryClassName)`
- parent字段：根模块的parent为null

## 经验总结

1. **API选择**: 优先验证API是否支持自定义字段，避免后期返工
2. **字段前缀**: Proxima平台的自定义字段需要特定前缀（r_test_manager_）
3. **模块管理**: Repository需要单独维护，支持层级创建
4. **并发控制**: 单个API并发调用比批量API更灵活可控
5. **错误处理**: 单个失败不影响整体，提高容错性
