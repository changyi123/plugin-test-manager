# 自动化测试集成 - 方案概要

## 一、业务目标
监听代码仓库的提交事件，自动识别测试代码的变更，将测试用例同步到测试管理平台，实现测试用例与代码的自动关联和维护。

## 二、系统架构

```
代码仓库 → Webhook → 队列存储 → 异步处理 → 用例同步 → 测试管理平台
                         ↓
                    管理页面(查看/重试)
```

## 三、核心流程

### 3.1 Webhook接收（同步）
1. 接收Code平台推送的webhook事件
2. 快速验证分支（只处理master或配置的分支）
3. 存储到队列表（status=pending）
4. 立即返回200响应

### 3.2 队列消费（异步）
1. 定时任务30秒执行一次
2. 获取pending状态的记录（每次最多5条）
3. 处理每个webhook事件：
   - 获取配置文件automation-test-map.json
   - 获取commit的diff
   - 过滤出测试文件
   - 解析测试用例
   - 同步到测试管理

### 3.3 用例同步规则
- 唯一标识：@TestId注解的值
- 存在则更新，不存在则创建
- 目录映射：根据配置文件中的路径映射

## 四、关键设计决策

### 4.1 为什么使用队列？
- Webhook需要快速响应（3秒内）
- 处理过程可能耗时（获取diff、解析代码、调用API）
- 支持失败重试
- 避免阻塞和超时

### 4.2 为什么需要配置文件？
- 明确哪些文件需要同步
- 定义测试文件与测试管理目录的映射关系
- 不是所有代码变更都需要处理

### 4.3 如何保证幂等性？
- 使用@TestId作为唯一标识
- 重复执行同步不会创建重复用例
- 通过IQL查询判断用例是否存在

## 五、技术栈
- 后端：TypeScript + Node.js
- 数据库：测试管理平台提供的Parse API
- 定时任务：trigger中的job模块
- API调用：@giteeteam/apps-team-api

## 六、部署方式
1. 开发环境：使用deploy-trigger.sh快速部署（跳过前端构建）
2. 生产环境：使用deploy.sh完整部署

## 七、监控与运维
- 同步记录表记录所有操作
- 失败记录支持手动重试
- 管理页面查看同步状态和统计

## 八、扩展性考虑
- 支持多种测试框架（JUnit、TestNG）
- 支持多分支同步（通过环境变量配置）
- 支持批量手动同步（管理页面功能）
