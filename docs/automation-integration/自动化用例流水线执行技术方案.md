# 自动化用例流水线执行技术方案












## 1. 需求概述

### 1.1 功能目标
- 为自动同步的测试用例增加流水线执行功能
- 通过iPipe流水线WebHook API触发自动化测试执行
- 提供Maven版本选择能力
- 区分自动化用例和手动用例的执行方式

### 1.2 业务流程
```
用例详情页面 → 识别自动化用例 → 显示"执行自动化用例"按钮 → 
选择Maven版本 → 调用iPipe API → 触发流水线执行 → 返回执行结果
```

## 2. 技术架构设计

### 2.1 系统架构
```
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   前端用例页面   │───▶│  后端API服务    │───▶│  iPipe流水线     │
│                │    │                │    │                │
│ - 执行按钮      │    │ - 版本管理      │    │ - WebHook触发   │
│ - 版本选择      │    │ - 流水线调用    │    │ - 测试执行      │
│ - 状态显示      │    │ - 结果回调      │    │ - 结果反馈      │
└─────────────────┘    └─────────────────┘    └─────────────────┘
```

### 2.2 数据流设计
```
测试用例数据 → 自动化标识判断 → UI渲染 → 用户操作 → 
API调用 → 流水线触发 → 执行监控 → 结果回调 → 状态更新
```

// POST /api/automation/execute - 触发自动化用例执行
export const executeAutomationCase = async (params) => {
  const { caseId, testId, mavenVersion } = params.body;
  
  // 1. 获取用例的自动化信息
  const caseInfo = await getCaseAutomationInfo(caseId);
  
  // 2. 构建流水线参数
  const pipelineParams = buildPipelineParams(caseInfo, mavenVersion);

  // 4. 记录执行日志

    caseId,
    testId,
    mavenVersion,
    executionStatus: 'pending',
    webhookResponse: result
  });
  
  return result;
};

#### 3.3.3 iPipe API集成
```typescript
interface PipelineWebHookParams {
  token: string;           // 认证token
  secret: string;          // 访问令牌
  materialParams?: string; // 物料参数(JSON字符串)
  allParams?: string;      // 全局参数(JSON字符串)
}

// iPipe WebHook调用
async function triggerPipelineExecution(params: {
  testId: string;
  filePath: string;
  className: string;
  methodName: string;
  mavenVersion: string;
  commitId: string;
}) {
  const { testId, filePath, className, methodName, mavenVersion, commitId } = params;
  
  // 构建物料参数
  const materialParams = JSON.stringify([{
    branch: "master",
    commitId: commitId,
    ciType: "MANUAL"  // 手动触发
  }]);
  
  // 构建全局参数
  const allParams = JSON.stringify({
    TEST_ID: testId,
    FILE_PATH: filePath,
    CLASS_NAME: className,
    METHOD_NAME: methodName,
    MAVEN_VERSION: mavenVersion,
    EXECUTION_TYPE: "SINGLE_TEST"
  });
  
  // 调用iPipe API
  const response = await axios.post('/api/ipipe/pipeline/rest/v1/openApi/webHook', {
    token: process.env.IPIPE_TOKEN,
    secret: process.env.IPIPE_SECRET,
    materialParams: encodeURIComponent(materialParams),
    allParams: encodeURIComponent(allParams)
  }, {
    headers: {
      'Content-Type': 'application/x-www-form-urlencoded'
    }
  });
  
  return response.data;
}
```

## 5. 错误处理和监控

### 5.1 异常处理策略
```typescript
// API调用异常处理
try {
  const result = await triggerPipelineExecution(params);
  return buildResponse({ success: true, data: result });
} catch (error) {
  // 记录错误日志
  await logExecutionError(caseId, error);
  
  // 更新执行状态
  await updateExecutionStatus(caseId, 'failed', error.message);
  
  return buildResponse({ 
    success: false, 
    error: '流水线触发失败，请检查配置或联系管理员' 
  });
}
```

### 5.2 执行状态监控

// 定时轮询执行状态 (可选，如果iPipe支持状态回调)
const pollExecutionStatus = async (executionId: string) => {
  const interval = setInterval(async () => {
    try {
      const status = await checkPipelineStatus(executionId);
      await updateExecutionStatus(executionId, status);

      }

## T3: 统一后端接口设计 (新增)

### 背景与目标
当前T1和T2的实现中，前端需要调用多个接口完成自动化执行，逻辑复杂且容易出错。T3的目标是将所有业务逻辑移到后端，前端只负责参数收集和单一接口调用。

### T3.1 架构设计原则
1. **单一职责**：前端只负责UI交互，后端负责业务逻辑
2. **统一接口**：所有自动化执行通过一个后端接口完成
3. **原子操作**：后端保证操作的原子性，失败时自动回滚
4. **错误处理**：完善的错误处理和状态回滚机制

### T3.2 统一接口规范

#### 接口定义
```
POST /api/automation/execute
```

#### 请求参数
```typescript
{
  testExecutionIds: string[];     // 测试执行ID列表
  mavenVersion: string;           // Maven版本
  jdkVersion: string;             // JDK版本
  triggerUser?: string;           // 触发用户（可选，后端从session获取）
  workspaceKey?: string;          // 工作空间（可选，后端从context获取）
}
```

#### 成功响应
```json
{
  "success": true,
  "data": {
    "executionId": "exec_20240115_143052_8f3a",
    "buildId": "pipe_build_12345",
    "pipeJumpUrl": "https://pipe.gitee.com/builds/12345",
    "message": "自动化测试已成功触发，执行ID: exec_20240115_143052_8f3a"
  }
}
```

#### 失败响应
```json
{
  "success": false,
  "error": {
    "code": "EXECUTION_RUNNING",
    "message": "以下测试执行正在进行中，请稍后再试: exec1, exec2",
    "details": {...}
  }
}
```

### T3.3 后端处理流程

#### 核心处理逻辑
```
1. 参数验证
   ├── 检查必填参数
   ├── 验证testExecutionIds格式
   └── 验证版本参数有效性

2. 状态检查
   ├── 查询每个testExecutionId的automation_status
   ├── 识别正在运行中的执行
   └── 如有运行中执行则抛出错误

3. 创建执行记录  
   ├── 生成唯一executionId
   ├── 记录到AutomationExecutionRecord表
   └── 状态设置为PENDING

4. 更新测试执行状态
   ├── 批量更新testExecutionIds的automation_status
   └── 设置为RUNNING状态

5. 调用Pipe流水线
   ├── 构建Pipe请求参数
   ├── 调用iPipe WebHook接口
   └── 获取buildId和跳转URL

6. 更新执行记录
   ├── 更新buildId和pipeJumpUrl
   ├── 状态更新为RUNNING
   └── 记录触发时间

7. 返回执行结果
```

#### 错误回滚机制
```
任何步骤失败时：
├── 回滚测试执行状态到FAILED
├── 记录错误信息到执行记录
├── 返回详细错误响应
└── 记录完整错误日志
```

### T3.4 错误码规范

| 错误码 | 描述 | 示例场景 |
|--------|------|----------|
| INVALID_PARAMS | 参数验证失败 | testExecutionIds为空 |
| EXECUTION_RUNNING | 有执行正在进行中 | 存在status为running的执行 |
| PIPE_CALL_FAILED | Pipe接口调用失败 | 网络超时或接口返回错误 |
| RECORD_CREATE_FAILED | 执行记录创建失败 | 数据库操作异常 |
| STATUS_UPDATE_FAILED | 状态更新失败 | 测试执行状态更新异常 |
| UNKNOWN_ERROR | 未知错误 | 其他未预期的错误 |

### T3.6 后端实现架构

#### 数据流设计
```
前端参数 → 参数验证 → 业务处理流程 → Pipe调用 → 响应返回

```

### T3.7 实现优势

1. **大幅简化前端**：从复杂的多步骤调用简化为单一接口调用
2. **提高可靠性**：后端统一处理，减少网络中断等导致的状态不一致
3. **更好的错误处理**：集中的错误处理和自动回滚机制  
4. **便于维护**：业务逻辑集中在后端，便于调试和优化
5. **性能优化**：减少前后端交互次数，提升响应速度
6. **事务完整性**：后端保证操作的原子性，避免部分成功的中间状态
